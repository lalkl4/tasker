# Архитектура

## Из чего состоит

```
        :80 :443
           │
        ┌──▼───┐   /                    ┌─────┐
        │caddy ├───────────────────────▶│ web │  nginx, статика
        │  TLS │   /api/*               └─────┘
        └──┬───┘   /.well-known/tasker
           │       /docs
           └───────────────────────────▶┌─────┐     ┌────┐
                                        │ api ├────▶│ db │  PostgreSQL
                                        └─────┘     └──▲─┘
                                      ┌─────────┐      │
                                      │ migrate ├──────┘
                                      └─────────┘
```

`migrate` — не служба, а разовая задача. Она отрабатывает и завершается, а
`api` объявлен зависимым от её **успешного завершения**, поэтому приложение
не поднимется на непромигрированной базе.

Веб и API живут под одним доменом. Из-за этого браузер обращается к API
относительными путями, и CORS в его случае не участвует вовсе. Настройка
`TASKER_CORS_ORIGINS` существует ради мобильного клиента — он приходит с
другого источника.

## Почему четыре репозитория

Продукту такого размера хватило бы одного. Разделение сделано осознанно —
ради опыта эксплуатации нескольких сервисов, а не потому, что монолит не
справлялся.

Ровно четыре, а не десять: десять репозиториев для двух человек означают,
что бóльшая часть времени уходит на согласование выпусков между ними.
Четыре дают всё, ради чего это затевается — кросс-репозиторный CI, реестр
образов, контрактную разработку и отдельный сборочный репозиторий.

Связь между ними — `openapi.json`. Сервер выкладывает его при каждом релизе,
клиенты сверяются с ним на сборке. Расхождение API и клиента всплывает в CI,
а не у пользователя.

## Как клиент подключается

Клиент не зашит под конкретную версию сервера. При подключении он спрашивает:

```
GET /.well-known/tasker

{
  "product": "tasker",
  "server_version": "1.4.2",
  "api_versions": ["v1"],
  "capabilities": ["auth.password", "projects", "tasks",
                   "tasks.search", "stats", "sync.updated_at"],
  "min_client": "1.0.0",
  "registration_open": true
}
```

Дальше он выбирает старшую версию API из тех, что понимает сам, и включает
функции **по списку `capabilities`, а не по номеру версии**.

Так сделано намеренно: исходники открыты, форки неизбежны, и номер чужой
сборки о её умениях ничего не говорит. Список умений — говорит.

## Обновление и откат

Развёрнутая версия — это переменная `TASKER_VERSION` в `.env`, а не свойство
образа. Поэтому откат сводится к правке одной строки.

`make update` делает: дамп базы → запомнить текущую версию → сменить версию →
забрать образы → `up -d --wait` → проверить.

`docker compose down` в этой последовательности намеренно нет. `up -d`
пересоздаёт только изменившиеся контейнеры, а `down` погасил бы и базу,
которая обновляться не собиралась. К тому же рядом с `down` живёт флаг `-v`,
который удаляет тома, — команду, которой в рабочем процессе нет, лучше и не
заводить в привычку.

`--wait` существенен: без него `up -d` возвращает успех, как только контейнеры
**запущены**, а не когда они работают. С ним compose дожидается healthcheck и
падает с ненулевым кодом, если не взлетело. Именно это делает обновление
шагом, который можно автоматизировать.

Подробнее про совместимость миграций при откате — [versioning.md](versioning.md).

## SaaS и self-hosted — один код

Разделять кодовую базу не нужно. Так живут GitLab, Sentry, Mattermost:
один код, разные конфигурации и топология развёртывания.

Отличия конфигурационные: открытая регистрация, тарифы, квоты, внешняя почта,
бэкапы в объектное хранилище. Ни одно из них не требует второй копии
приложения. Разница выражается переменной режима и оверлеем compose поверх
базового файла.

Самохостер получает `compose.yaml` — пять сервисов и одну команду. Боевой
инстанс запускает те же пять плюс оверлей с биллингом, фоновым обработчиком
и наблюдаемостью.

## Что где отвечает

| Слой | За что | Вопрос, на который отвечает |
|---|---|---|
| Terraform | VPS, DNS, фаервол, бакет для бэкапов | что существует |
| Ansible / cloud-init | пакеты, docker, пользователь, `/opt/tasker` | как настроен хост |
| Docker Compose | сервисы, сети, тома | что запущено |
| CI/CD | сборка образов, тег версии в `.env` | какая версия запущена |

Terraform контейнерами не управляет. Провайдер `docker_container` существует,
но его использование вместо compose даёт два источника правды: состояние в
`tfstate` расходится с реальностью при первом же ручном перезапуске.

Браться за Terraform стоит после того, как заработают compose и CI, — иначе
отлаживаются две незнакомые системы одновременно. Существующий сервер
пересоздавать не придётся: `terraform import` втянет его как есть.

## Порядок освоения

1. **Репозитории и сборка** — готово: CI гоняет тесты и публикует образы
2. **Управляемое развёртывание** — готово: compose, миграции отдельным шагом,
   версия переменной, бэкапы, `make update` и `make rollback`
3. **Наблюдаемость** — Prometheus, Loki, Grafana
4. **Непрерывная доставка** — тег запускает выкладку, после неё проверки,
   при неуспехе автоматический откат
5. **Инфраструктура как код** — Terraform и Ansible
6. **Оркестрация** — k3s, Helm, обновление без простоя; только для боевого
   инстанса, самохостеру по-прежнему отдаётся compose

Каждая ступень опирается на предыдущую. Оркестратор поверх непонятного
развёртывания не чинит развёртывание, а прячет его за ещё одним слоем.
