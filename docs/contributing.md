# Как ведётся разработка

## Обычный день разработчика

Захотелось поправить код — порядок такой:

```bash
# 1. свежий main
git switch main && git pull

# 2. ветка от него; имя говорит, что делаем
git switch -c feat/task-assignees

# 3. правим, запускаем локально
make dev                    # в репозитории tasker
pytest                      # в репозитории tasker-api

# 4. коммит в формате, который потом прочитает генератор версий
git commit -m "feat(tasks): назначение задачи на участника"

# 5. отправляем и открываем pull request
git push -u origin feat/task-assignees
gh pr create --fill
```

Дальше работает CI: линтер, тесты на SQLite и PostgreSQL, проверка
расхождения моделей с миграциями. Пока проверки красные, вливать нельзя.

После слияния в `main` собирается образ `:main` — его можно погонять на
стенде. В прод он не идёт: туда попадает только тег релиза.

## Ветки

Живут **коротко** — часы или день-два, не недели. Чем дольше ветка живёт
отдельно, тем больнее слияние: это не вопрос дисциплины, а арифметика
расхождения.

| Префикс | Для чего |
|---|---|
| `feat/` | новая возможность |
| `fix/` | исправление |
| `chore/` | зависимости, конфиги, документация |
| `refactor/` | перекладывание кода без смены поведения |

Если задача не влезает в пару дней — её нужно резать, а не растить ветку.
Крупное изменение вливается по частям, а недоделанная часть прячется за
флагом (см. ниже).

## Сообщения коммитов

Формат Conventional Commits:

```
<тип>(<область>): <что сделано>
```

Типы: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `perf`, `ci`.
Восклицательный знак или строка `BREAKING CHANGE:` означает ломающее изменение.

Это не бюрократия: из этих префиксов автоматически считается следующая версия
и собирается CHANGELOG. Подробнее — [versioning.md](versioning.md).

## Как это устроено в больших компаниях

Вы спрашивали, чем их процесс отличается. Отличий немного, и почти все они
решают проблемы масштаба.

### Trunk-based development

Господствующий подход в крупных инженерных организациях: **одна долгоживущая
ветка** (`main`), от неё короткие ветки, которые вливаются обратно за часы.
`main` всегда пригоден к выпуску.

Противоположность — Git Flow с ветками `develop`, `release/*`, `hotfix/*`.
Он был стандартом в 2010-х, сейчас считается избыточным для большинства
команд: три уровня веток нужны, когда вы поддерживаете несколько версий
одновременно у заказчиков. Кстати, для self-hosted это отчасти ваш случай —
если однажды придётся выпускать исправления к 1.x, когда main уже на 2.x,
появится ветка `release/1.x`. До тех пор она не нужна.

### Что добавляют сверху

**Защита ветки.** В `main` нельзя пушить напрямую, только через pull request,
и только с зелёными проверками. Это первое, что стоит включить, — оно
бесплатно и сразу.

**Обязательное ревью и CODEOWNERS.** Файл, где написано, кто владеет какими
каталогами; ревьюеры назначаются автоматически.

**Squash merge.** Ветка вливается одним коммитом. История `main` становится
линейной и читаемой: один коммит — одно осмысленное изменение.

**Merge queue.** Когда десятки людей вливают одновременно, каждый PR
проверялся на устаревшем `main`. Очередь слияний перепроверяет изменения
на актуальной вершине по одному. Проблема появляется где-то с десятка
разработчиков.

**Preview-окружения.** На каждый pull request поднимается временный стенд
со своей базой. Ревьюер не читает диф, а щёлкает по живому.

**Флаги функциональности.** Код вливается в `main` недоделанным, но выключенным.
Это то, что делает короткие ветки возможными: не надо держать ветку месяц,
пока функция не готова целиком. Включение и выключение — не выпуск, а
переключатель, поэтому и откат мгновенный.

**Постепенная выкатка.** Новая версия сначала получает 1% трафика, потом
10%, потом всё. При росте ошибок откат автоматический.

### Что из этого брать вам, а что нет

| Практика | Когда внедрять |
|---|---|
| Защита `main` + обязательные проверки | **сразу**, это бесплатно |
| Squash merge | **сразу** |
| Conventional Commits | **сразу** |
| Ревью | как только появится второй человек |
| Preview-окружения | когда ревью станет регулярным |
| Флаги функциональности | когда появится изменение, не влезающее в пару дней |
| Merge queue | от десятка разработчиков; вам не понадобится |
| Постепенная выкатка | вместе с оркестратором, ступень 6 |

Главное — не тащить всё сразу. Merge queue при одном разработчике решает
несуществующую проблему и добавляет минуту ожидания к каждому слиянию.

## Выпуск релиза

```bash
# всё, что нужно, уже в main и зелёное
git switch main && git pull
git tag v1.5.0
git push --tags
```

Дальше CI сам: собирает образы с номером из тега, публикует в GHCR,
прикладывает `openapi.json` к релизу. На сервере:

```bash
cd /opt/tasker
make update VERSION=1.5.0
```

## Локальная разработка

В сборочном репозитории:

```bash
make dev
```

Поднимает стек из **соседних репозиториев** — ожидается, что они лежат рядом:

```
~/projects/
  tasker/          ← отсюда запускаете
  tasker-api/
  tasker-web/
```

Исходники смонтированы внутрь контейнеров, сервер перезапускается сам при
правке файла, порт PostgreSQL открыт наружу — можно подключиться psql.

### Когда меняете схему

```bash
cd tasker-api

# 1. поменяли app/models.py

# 2. сгенерировали миграцию
alembic revision --autogenerate -m "add task assignee"

# 3. ОТКРЫЛИ файл и прочитали
#    autogenerate не видит переименований и показывает их как
#    удаление плюс добавление — то есть как раз разрушающее изменение
#    вместо безопасного

# 4. проверили в обе стороны
alembic upgrade head
alembic downgrade -1
alembic upgrade head

# 5. тесты, включая проверку расхождения моделей с миграциями
pytest
```

Имя миграции пишите латиницей: кириллица попадает в имя файла и ловит
проблемы с кодировкой на других системах.
