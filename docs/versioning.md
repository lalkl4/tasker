# Версии

## Версия хранится ровно в одном месте

Самая частая беда в проектах из нескольких репозиториев — номер версии,
записанный в пяти файлах. Один забыли обновить, и дальше никто не знает,
что на самом деле развёрнуто.

Здесь версия записана **только в git-теге**. Больше нигде: ни в
`pyproject.toml`, ни в `VERSION`-файле, ни в исходниках.

```
git tag v1.4.2 && git push --tags
        │
        ▼
   CI в tasker-api
        │  docker/metadata-action берёт номер из тега
        ▼
   docker build --build-arg VERSION=1.4.2
        │
        ▼
   ghcr.io/lalkl4/tasker-api:1.4.2
                            :1.4
                            :sha-9f3c1a2
        │
        ▼
   /opt/tasker/.env → TASKER_VERSION=1.4.2
        │
        ▼
   GET /.well-known/tasker → {"server_version": "1.4.2"}
```

В коде вместо номера — чтение переменной, которую подставила сборка:

```python
# app/config.py
SERVER_VERSION = os.environ.get("TASKER_BUILD_VERSION") or "0.0.0+dev"
```

Запасное значение `0.0.0+dev` намеренно бросается в глаза: если сервер
отдаёт его в проде, значит образ собран мимо CI.

Мест, где версия существует, ровно два, и второе выводится из первого:

| Где | Что означает |
|---|---|
| git-тег | что выпущено |
| `TASKER_VERSION` в `.env` на сервере | что развёрнуто |

## Какой номер ставить

Обычный SemVer — `МАЖОР.МИНОР.ПАТЧ`, но важно, что именно здесь считается
ломающим изменением.

| Часть | Когда растёт | Пример из этого проекта |
|---|---|---|
| МАЖОР | ломается совместимость с клиентами или требуется ручное вмешательство при обновлении | 2.0.0: появилась авторизация, API переехал с `/api/` на `/api/v1/` |
| МИНОР | новая возможность, старые клиенты продолжают работать | добавили назначение задачи на участника |
| ПАТЧ | исправление, поведение не менялось | починили подсчёт просрочки |

Отдельно стоит запомнить: **версия продукта и версия API — разные вещи и
меняются с разной скоростью.**

`/api/v1` останется `v1` через много выпусков продукта. Версия API растёт,
только когда ломается контракт: убрали поле, изменили смысл ответа. А новые
возможности клиент узнаёт не по номеру, а из списка `capabilities` в
`/.well-known/tasker` — так работает даже с чужим форком, о версии которого
мы ничего не знаем.

## Сборки из веток и релизы

CI собирает образ на каждый пуш в `main`, но с другими тегами:

| Тег образа | Откуда | Куда годится |
|---|---|---|
| `1.4.2` | git-тег `v1.4.2` | **прод** |
| `1.4` | он же | прод, если хотите автоматически получать патчи |
| `main` | пуш в main | стенд, попробовать |
| `sha-9f3c1a2` | любой пуш | воспроизвести конкретный коммит при разборе |

**Правило: в проде запускается только тег релиза.** `main` — движущаяся
цель: сегодня это один код, завтра другой, а `.env` выглядит одинаково.
Тогда «что развёрнуто» перестаёт быть ответом.

## Автоматизация номера

Ставить теги руками — нормально и понятно. Когда захочется убрать ручной шаг,
стандартный путь такой:

**1. Conventional Commits** — договорённость о формате сообщений:

```
feat(tasks): назначение задачи на участника
fix(auth): не пропускать истёкший токен
feat(api)!: убрать поле notes

BREAKING CHANGE: клиенты 1.x перестанут работать
```

Префикс определяет часть версии: `fix:` → патч, `feat:` → минор,
`!` или `BREAKING CHANGE:` → мажор.

**2. release-please** — экшен, который читает историю коммитов, сам считает
следующий номер, собирает CHANGELOG и открывает pull request «Release 1.5.0».
Вы его смотрите и вливаете — тег ставится автоматически, а дальше работает
уже существующий CI.

Смысл в том, что решение о версии перестаёт быть вашим суждением и становится
следствием того, что реально изменилось в коде.

**Когда это внедрять.** Не сразу. Сначала научитесь ставить теги руками и
посмотрите, как через них проходит вся цепочка. Автоматика поверх процесса,
который вы не понимаете, прячет процесс, а не упрощает его. Договорённость
о формате коммитов при этом полезна с первого дня — она бесплатна и даёт
читаемую историю.

## Миграции и откат

Полный разбор — в [записке об архитектуре](architecture.md), здесь кратко
самое важное.

**Код откатывается мгновенно, данные не откатываются вообще.** При откате
образ становится прежним, а схема базы остаётся новой: миграцию вы не
отменяете. Отсюда правило:

> Миграция версии **N** обязана оставаться совместимой с кодом версии **N−1**.

Поэтому разрушающие изменения растягиваются на несколько выпусков — приём
называется expand/contract. Переименование колонки `notes` в `description`:

| Выпуск | Что делает | Почему безопасно |
|---|---|---|
| 1.5 | добавить `description`, писать в обе | код 1.4 новой колонки не знает и игнорирует |
| 1.6 | перелить данные, читать из новой | код 1.5 тоже писал в обе |
| 1.7 | перестать писать в `notes` | схема не меняется |
| 1.8 | удалить `notes` | код 1.7 её уже не трогал |

Окно отката — один выпуск. Прыгнуть с 1.8 сразу на 1.4 нельзя, и это
нормально: так устроено везде.

`downgrade()` в Alembic писать стоит, он полезен в разработке. Но в бою на
него не опираются: структуру он вернёт, содержимое удалённой колонки — нет.

## Проверки, которые это защищают

В CI репозитория `tasker-api`:

- **тест на расхождение** — после `alembic upgrade head` схема в базе
  сравнивается с моделями; поймали забытую миграцию;
- **тест на обратимость** — цепочка миграций разворачивается вниз и обратно;
- **прогон на обеих СУБД** — один и тот же набор тестов на SQLite и на
  PostgreSQL, потому что поддерживаются обе.

Чего пока нет и что стоит добавить: прогон миграций **на копии боевых данных**.
Миграция может прекрасно работать на пустой таблице и упереться в реальных
данных — например, в дубликаты при добавлении уникального индекса.

## Два реестра и зачем это

Образы публикуются в **GHCR** и зеркалятся в **Docker Hub**. У каждого своя роль.

| | GHCR | Docker Hub |
|---|---|---|
| Что попадает | каждая ветка и коммит | только теги релизов |
| Роль | рабочий реестр CI | витрина, куда приходят люди |
| Вход из Actions | встроенный `GITHUB_TOKEN` | access token в секретах |
| Лимит на скачивание | нет | 100 в час на IP анонимно |

**Почему канонический реестр — GHCR.** Публикация идёт по встроенному
`GITHUB_TOKEN`: нет секрета, который надо заводить в трёх репозиториях,
хранить и ротировать. И нет лимита на скачивание — а он реален: Docker Hub
отдаёт `ratelimit-limit: 100;w=3600`, и за общим адресом провайдера эта сотня
делится на всех соседей.

**Почему всё же нужен Docker Hub.** Это место, куда люди идут искать образы.
`docker pull lalkl4/tasker-web` — привычная форма, а GHCR всегда требует
явного префикса `ghcr.io/`, потому что реестр по умолчанию — Docker Hub. Для
продукта, который отдаётся незнакомым людям, это прямо влияет на то, дойдут
ли они до установки.

**Зеркало не пересобирает образ.** `docker buildx imagetools create` копирует
готовый multi-arch манифест между реестрами. Если бы зеркало собиралось
заново, в Docker Hub уехал бы другой набор слоёв — и утверждение «везде один
и тот же образ» перестало бы быть правдой.

### Как включить

Задача зеркалирования выключена по умолчанию и молча пропускается. Чтобы
включить, в каждом из репозиториев `tasker-api` и `tasker-web`:

1. Settings → Secrets and variables → Actions
2. Секреты: `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN`
   (токен создаётся в Docker Hub → Account Settings → Personal access
   tokens, права Read & Write)
3. Переменная: `DOCKERHUB_MIRROR` = `true`

Выключателем сделана именно **переменная**, а не наличие секрета: секреты
недоступны в условии `if` на уровне задачи, и без переменной сборка по тегу
падала бы у всех, кто форкнул репозиторий и токена не заводил.

### Незакрытый хвост

В Docker Hub лежит `lalkl4/tasker` — образ версии 1.0.0, собранный ещё до
разделения на репозитории. Он **несовместим со всем нынешним**: там нет
авторизации, API без версии, схема другая. Любой, кто сейчас сделает
`docker pull lalkl4/tasker`, получит его.

Разумно либо описать на его странице, что образ устарел и куда идти, либо
удалить репозиторий. Само оно не рассосётся.
